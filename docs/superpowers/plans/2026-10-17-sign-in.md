# Sign-in Implementation Plan: Tailscale identity and passkeys

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** People use the web app as themselves: a Tailscale identity when they come through `tailscale serve`, otherwise a passkey (Face ID / Touch ID) registered from an invite Noah issues. The admin API key keeps working for non-browser clients.

**Architecture:** A new `airlie.auth` package: a SQLite user store, an auth resolver that turns a request into a `Principal` (Tailscale header → session cookie → Bearer key), WebAuthn ceremonies with the `webauthn` library, and a FastAPI router at `/v1/auth`. serve's key middleware is replaced by that resolver. The web app's sign-in screen gains "Use this device" (passkey) and the join page.

**Tech Stack:** Python 3.12, `webauthn` (py_webauthn, add to `pyproject.toml`), stdlib `sqlite3`, FastAPI, the web app's ES modules (`navigator.credentials`).

**Spec:** `docs/superpowers/specs/2026-10-16-remote-studio-design.md`, section "Who gets in" (Identity, revised 2026-10-17), and `2026-10-17-web-app-and-local-board-design.md` for the app.

## Global Constraints

- Trust `Tailscale-User-Login` only when `auth.tailscale: true` AND the request's client address is loopback (that is where `tailscale serve` proxies from); otherwise ignore the header.
- A Tailscale login is accepted only when a user with that login exists in the store; unknown logins get 401 with `{"error": "not invited"}`.
- Passkeys: `auth.rp_id` (default: the request's host without port), `auth.origins` (default: `https://<rp_id>` plus `http://localhost:*` and `http://127.0.0.1:*`); registration requires an unexpired invite token; `user_verification: required`.
- Sessions: an `airlie_session` cookie, `HttpOnly`, `SameSite=Strict`, `Secure` when the request is https, 30 days, stored server-side (`sessions` table) so revoking a user ends their sessions.
- The Bearer key (`--api-key`) still authenticates and is the `admin` principal named `api-key`.
- Store: `observability.state_dir / "auth.sqlite"`, WAL. Nothing from it is logged.
- Tests: no network; `task check` passes. Commits end with `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>`.

## Review Focus

- A request with a forged `Tailscale-User-Login` header from a non-loopback address must be refused even when `auth.tailscale` is on. (Task 3 test `test_tailscale_header_is_ignored_off_loopback`.)
- An invite used twice, or after expiry (24 h), must fail registration with 410. (Task 4.)
- Deleting a user must invalidate their sessions and passkeys at once. (Task 2 and Task 3 tests.)
- When no user exists yet (fresh install) and no API key is set, `/v1` must still be reachable from loopback only, so `task auth:admin` can bootstrap; from anywhere else 401. (Task 3 `test_fresh_install_is_loopback_only`.)
- A passkey assertion with a stale `sign_count` (cloned authenticator) must be refused and logged as an event. (Task 4.)

### Task 4: Passkey registration and login API

**Files:**
- Create: `src/airlie/auth/api.py` (`auth_router(store, resolver, cfg) -> APIRouter` at `/v1/auth`)
- Modify: `src/airlie/serve/app.py` (`include_router`)
- Test: `tests/unit/test_auth_api.py` (use `webauthn`'s own helpers or recorded fixtures to build valid registration/assertion responses; no browser)

**Interfaces (routes):**
- `GET /v1/auth/me` → the principal (401 when none).
- `POST /v1/auth/invites` (admin) `{"name", "role"?, "login"?}` → `{"url": "/#/join/<token>", "expires_at"}`.
- `GET /v1/auth/users` (admin) → users with credential counts; `DELETE /v1/auth/users/{id}` (admin).
- `POST /v1/auth/register/options` `{"invite"}` → WebAuthn creation options (challenge kept server-side, 5 min); `POST /v1/auth/register/verify` `{"invite", "credential"}` → sets the session cookie, 201; invite problems → 410.
- `POST /v1/auth/login/options` → request options (discoverable credentials); `POST /v1/auth/login/verify` `{"credential"}` → session cookie; stale sign_count → 401 and an `auth_refused` event in serve's log.
- `POST /v1/auth/logout` → clears the session.
- These routes are exempt from the 401 middleware except `me`, `invites`, `users`.

- [ ] Tests → fail → implement → pass → commit `feat(auth): passkey registration and login`.
